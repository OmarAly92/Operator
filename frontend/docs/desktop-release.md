# Desktop release runbook

How to cut a desktop release, end to end. This describes the **Tauri** pipeline
(task 18): `tauri build` produces every platform bundle plus signed updater
archives, `scripts/tauri-feed.mjs` generates both feed families, and
`scripts/verify-tauri-artifacts.sh` is the pre-release gate. The Electron/Forge
pipeline this document previously described is retired; the installed Electron
fleet keeps updating through the compatibility YAML feeds we still publish.

## How releases work

- **Stable** releases are triggered by pushing a `desktop-vX.Y.Z` tag to
  `OmarAly92/operator`. `.github/workflows/frontend-release.yml` builds on four
  runners (macOS arm64, macOS Intel, Windows, Linux), signs and notarizes the
  macOS builds, signs every updater archive with the Tauri minisign key, and
  publishes a GitHub Release keyed off `frontend/package.json`'s version
  (`v<version>`).
- **Nightly** builds are the same pipeline with the `nightly` channel:
  versions look like `0.10.4-nightly.<YYYYMMDDHHMM>` and their feeds carry the
  escalation flag (`--important`). No nightly schedule workflow exists on this
  branch yet; cutting one reuses `tauri-feed.mjs` with `nightly` as channel.
- The version source of truth is `frontend/package.json` `"version"`, which the
  Tauri config reads (`"version": "../package.json"`); the release tag must be
  cut on a commit carrying the right version.
- Feature (`pr<N>`) releases work exactly as before — see their section below.

## Feed model (two families per release)

Every release publishes BOTH families so old and new shells both update:

1. **Tauri updater JSON** — `latest.json`, `nightly.json`, `pr<N>.json`.
   Canonical v2 updater manifests: `{version, notes, pub_date, platforms}` with
   one entry per canonical target (`darwin-aarch64`, `darwin-x86_64`,
   `linux-x86_64`, `windows-x86_64`), each carrying the archive URL and its
   base64 minisign signature. Generated by:

   ```bash
   node scripts/tauri-feed.mjs <dist-dir> <version> <channel> \
     [--release-date <iso>] [--important] [--notes <text>]
   ```

2. **Electron-compatibility YAML** — `latest.yml`, `latest-mac.yml`,
   `latest-linux.yml` (and `nightly*` / `pr<N>*` equivalents), consumed by
   electron-updater in the installed fleet. Generated by the same invocation;
   `tauri-feed.mjs` delegates to `scripts/feed.mjs`. These point at the ditto
   zip (mac), NSIS installer (win) and AppImage (linux) of the SAME Tauri
   release — that is how an Electron install migrates to Tauri. They never
   carry `.blockmap` sidecars: full downloads only, same reasoning as #3267
   decision 4.

Channel isolation is enforced twice: the builder refuses any cross-channel
asset or filename, refuses invalid semver, wrong-architecture archives,
missing `.sig` sidecars, insecure (non-https, non-loopback) URLs, duplicate
platforms, and ANY private-key material in the dist directory; and the feature
workflow's guard step rejects any generated `latest*`/`nightly*` manifest
(#2270 poisoning class).

## Artifacts per stable release

| Artifact | Purpose |
| --- | --- |
| `operator-darwin-{arm64,x64}-<ver>.zip` | Permanent macOS zip; target of `latest-mac.yml` |
| `operator-darwin-{arm64,x64}.dmg` (+ versioned copies) | First-install container |
| `operator-darwin-{arm64,x64}-<ver>.app.tar.gz` (+ `.sig`) | Tauri mac updater archive |
| `Operator_<ver>_x64-setup.exe` (+ `.sig`) | Windows NSIS installer + updater archive |
| `operator_<ver>_amd64.AppImage` (+ `.sig`) | Linux AppImage + updater archive |
| `operator_<ver>_amd64.deb`, `operator-<ver>.x86_64.rpm` | System packages |
| `latest.json` + `latest*.yml` | Feeds |
| Version-free aliases: `operator-darwin-arm64.zip`, `operator-darwin-x64.zip`, `operator-darwin-arm64.dmg`, `operator-darwin-x64.dmg`, `operator-win32-x64.exe`, `operator-linux-x64.AppImage` | `opr start` / landing page constants — never renamed |

Every base artifact bundles the Go daemon, agent-browser 0.33.1, the Node
22.23.2 ACP runtime, licenses, and the app icons; `npm run verify:tauri-artifacts`
inspects all of them INSIDE each package before feeds may be generated.

## Hard rule: exactly one publisher

**Only the designated release conductor runs a real publish.** There is no ad
hoc human-triggered publish outside that identity, on any channel, for any
reason, including "just this once to test something".

Why this is a rule and not a preference: between 22 and 24 Jul two different
publishers emitted divergent macOS zip formats on alternating days. When the
28-29 Jul signing incident hit, the evidence was unreadable. A single publisher
makes consecutive releases byte-comparable, so a real regression shows up as a
real difference.

Verification of artifacts is a separate concern and is not owned by any single
identity: anyone can run

```bash
cd frontend && npm run verify:tauri-artifacts -- --dist <dir>
```

which checks structure, bundled resources and signature sidecars. Its ledger
has three classes: FAIL (structural violation, or a trust check attempted and
failed on this host — exits 1), GATE (needs conductor-held material even on a
fully equipped CI host: Authenticode evidence, rpm -K against the conductor
key, NSIS smoke install; recorded by name, never fatal), and SCOPE-SKIP
(artifact-class absence caused by matrix topology). Pass
`--arch arm64` / `--arch x64` to declare which arches a dist must carry:
out-of-scope classes print an INFO line instead of a ledger row, so a
single-arch matrix leg is not punished for its sibling's absence.
`--strict-trust` means exactly: every check applicable to the declared scope
that is executable on this host ran and PASSED — gates stay recorded and
non-fatal, but the macOS codesign/spctl/staple trio failing under it DOES fail
the run, because trust must be able to fail a release.
For a single macOS artifact use `scripts/verify-mac-artifact.sh` — the only
supported way to check seal/notarization/staple by hand (it accepts `.zip`,
`.app`, `.dmg`, and since task 18 the Tauri `.app.tar.gz`, extracting each with
its seal-preserving tool).

## Prerequisites

Secrets/variables (repo level):

- `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_API_KEY_BASE64`, `APPLE_API_KEY_ID`,
  `APPLE_API_ISSUER`, `APPLE_SIGNING_IDENTITY` — macOS signing + notarization
  (consumed by `.github/actions/macos-signing-setup`; notarization now goes
  through `xcrun notarytool` + `xcrun stapler` in the workflow).
- `TAURI_SIGNING_PRIVATE_KEY` (+ optional `_PASSWORD`) — minisign key whose
  PUBLIC half must also be set as the variable `OPERATOR_UPDATER_PUBLIC_KEY`;
  it is compiled into the shell at build time and a build without it fails
  closed. Generate with `npx tauri signer generate`; NEVER commit the private
  half anywhere.

## Cutting a stable release

### 1. Decide the version and review what ships

Same as before: bump `frontend/package.json` on master via a PR, merge, then
tag the merge commit `desktop-vX.Y.Z`.

### 2. Approve the `release` environment

The run waits under Actions > "Desktop release". An approver approves the
environment deployment; see "Who can approve releases" below.

### 3. What the workflow does

Per runner: checkout, npm/go/rust setup, daemon + agent-browser + ACP runtime
prebuilds, then `npm run tauri:release`
(`tauri build --config src-tauri/tauri.release.conf.json`, which enables
updater artifacts and bakes the production feed base URL). On macOS it then
verifies the seal, submits for notarization, staples the `.app` and `.dmg`,
cuts the permanent ditto zip with `scripts/package-tauri-mac-zip.sh` (exactly
`ditto -c -k --sequesterRsrc --keepParent`), renames the updater archives,
uploads everything to the `v<version>` release, and pushes the platform's
version-free aliases with `--clobber`.

After all legs: `publish-feed` downloads the release assets and runs
`node scripts/tauri-feed.mjs dist <version> latest`, uploading `latest.json` +
`latest*.yml`. `e2e-gate` remains advisory pod smoke against the published
Linux AppImage.

### 4. Verify

```bash
gh release view vX.Y.Z -R OmarAly92/operator --json assets --jq '.assets[].name'
curl -sL https://github.com/OmarAly92/operator/releases/latest/download/latest.json | jq '.version, (.platforms|keys)'
gh release download vX.Y.Z -R OmarAly92/operator --pattern 'operator-darwin-arm64.zip' --dir /tmp/relcheck
frontend/scripts/verify-mac-artifact.sh /tmp/relcheck/operator-darwin-arm64.zip
```

If a leg fails, re-run the failed jobs; alias and feed uploads use `--clobber`,
so re-runs replace assets safely.

## Fork test releases (dev loop)

Test releases go to the fork, never to OmarAly92: push a `desktop-v*` tag to
the fork or dispatch the workflow from the fork's Actions tab. Releases publish
to whatever repository the workflow runs in. Unsigned local builds behave like
testing builds: `npm run tauri:build` (base config, no updater artifacts).

## Testing builds

`testing-build.yml` is the ONLY desktop testing pipeline (the former
`desktop-testing.yml` was retired with the Forge pipeline). It builds unsigned
bundles on all three OSes for a `0.0.0-testing-*` tag or manual dispatch,
inspects package resources with
`./scripts/verify-tauri-artifacts.sh --mode testing` (missing updater
signatures are recorded as gates there, not failures), smoke-installs the NSIS
installer on Windows, and lists deb/rpm contents on Linux.

## Feature releases

A **feature release** is a signed, installable build of a single **unmerged**
PR, cut manually so the PR can be dogfooded or demoed in isolation. It ships as
a GitHub prerelease on the isolated `pr<N>` channel and writes only
`pr<N>.json` + `pr<N>*.yml` — never `latest*`/`nightly*` (enforced by the
builder AND by a guard step in `feature-release.yml`).

### Cutting a build

1. **Actions > Desktop feature release > Run workflow** with inputs:

   | Input        | Required | Description                                            |
   | ------------ | -------- | ------------------------------------------------------ |
   | `pr`         | Yes      | PR number to build. Must be open at dispatch time.     |
   | `slug`       | No       | Display-only label; never in the version or tag.       |
   | `platforms`  | No       | Comma-separated `mac,win,linux` (default: all three).  |
   | `allow_fork` | No       | Set `true` to build a cross-repository PR.             |

2. The `guard` job (no secrets, inspectable) enforces the 5-live-builds quota,
   confirms the PR is open, and computes `<base>-pr<N>.<UTCts>+<sha>` via the
   contents API without checking out or executing anything from the PR head.
3. Build jobs pause for `release`-environment approval. **The approver must
   inspect the PR's head SHA before approving**: these jobs build unmerged code
   with access to the signing secrets.
4. After approval each leg runs `npm run tauri:release` (macOS additionally
   notarizes/staples/cuts the zip), verifies artifacts, uploads to the
   `v<version>` prerelease; `publish-feed` generates the `pr<N>` feeds, runs
   the latest*/nightly* rejection guard, deletes prior releases for the same
   PR (one live build per PR), and annotates the release with the marker
   ```
   <!-- opr-feature-build: {"pr":<N>,"base":"<base>","sha":"<sha>","slug":"<slug>"} -->
   ```
   which the shell's feature-builds listing parses (7-day expiry, quota,
   retirement).

### How users consume feature releases

Unchanged: Developer Mode exposes the Feature Releases channel under
Settings > Updates; picking a PR pins `pr<N>` while preserving the home
channel; return-home resolves the home feed (downgrades allowed);
retirement clears the pin automatically on the next poll. Update settings live
in the Go settings store now (`PATCH /api/v1/settings/updates`), replacing the
old Electron-side `update-settings.json`.

## Post-release monitoring

`mac-update-e2e.yml` installs the published N-1 zip alias on a clean macOS
runner, points it at the REAL published feed, and proves the engine stages N
(`--expect-stage-only`, current mode while the project-owned verified apply
path is pending) or performs the full quit-swap-relaunch-liveness cycle
(`full-install`, once apply lands). It is monitoring, NOT a promotion gate —
it finishes after the release it watches has already shipped. The
`release-latest-guard.yml` hourly cron asserts `/releases/latest` is a stable
semver release carrying `latest.json`, the three compat YAMLs, the aliases, and
that `latest.json` covers all four platforms with non-empty signatures.
