title: Built-in capabilities

---

Operator's current Go backend uses built-in adapters and services. These capabilities ship with the desktop app; they are not npm plugins and cannot be installed through a marketplace.

## Capability map

| Area | Shipped support | Selection |
| --- | --- | --- |
| [Agents](/docs/plugins/agents) | 24 terminal agent adapters | Per project or session |
| [Runtime](/docs/plugins/runtimes) | `tmux` on macOS/Linux; ConPTY on Windows | Automatic by platform |
| [Workspace](/docs/plugins/workspaces) | Git worktrees and Operator-managed Scratch directories | Automatic by project kind |
| [Tracker](/docs/plugins/trackers) | GitHub issue intake | Per-project, opt-in |
| [SCM](/docs/plugins/scm) | GitHub PR, checks, reviews, and mergeability | Derived from the Git repository |
| [Notifications](/docs/plugins/notifiers) | Durable in-app history and native desktop toasts | Built in |
| [Terminal](/docs/plugins/terminals) | Desktop xterm surface over Operator's terminal mux | Built in |

## Agents are the configurable adapter set

Use `opr agent ls --refresh` to see the exact daemon-advertised catalog and whether each local CLI is installed and authenticated. `opr spawn --agent <name>` selects a harness for one session; project worker and orchestrator defaults are stored in typed project configuration.

The other areas are daemon-owned boundaries, not interchangeable marketplace slots. In particular, the runtime is selected for the operating system, Git repositories use worktrees, and Scratch projects use Operator-managed directories.

<Callout type="info">
	Legacy `operator.yaml` plugin, notifier, runtime, workspace, tracker, and SCM blocks are not active configuration in the rewrite. `opr import` reports unsupported legacy fields as dropped.
</Callout>
