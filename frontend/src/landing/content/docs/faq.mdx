---
title: FAQ
description: Common questions about the current Operator desktop product.
---

<Accordions expandAll>
	<Accordion title="How is Operator different from several agent terminals?">
		Operator adds isolated worktrees, durable session identity, Chat or TUI control, pull-request observation, lifecycle reactions, review runs, notifications, and external browser previews around those agents.
	</Accordion>

	<Accordion title="Do I have to use Claude Code?">
		No. Operator includes adapters for more than twenty harnesses, including Claude Code, Codex, Cursor, Aider, OpenCode, Droid, Kimi Code, and others. Native Chat currently supports installed Codex, Claude Code, OpenCode, and Droid; other harnesses use Terminal UI.
	</Accordion>

	<Accordion title="Does Operator merge pull requests?">
		Operator provides a merge action, but merging is a deliberate user or workflow decision, not an unconditional default. Review code and repository policy before requesting a merge.
	</Accordion>

	<Accordion title="Which source-control systems are supported?">
		GitHub is the shipped SCM observer in the current Go rewrite. It supplies pull-request, CI, review, and mergeability facts. Historical docs listed broader GitLab and tracker plugins; those integrations are not all active in the current daemon lifecycle.
	</Accordion>

	<Accordion title="Does Operator need webhooks?">
		No. The current GitHub SCM observer polls with authentication, ETag guards, and semantic diffing. Live desktop updates come from the daemon's SQLite CDC event stream.
	</Accordion>

	<Accordion title="Does it work on Windows?">
		Yes. Windows supports the desktop app, Chat, and native Terminal UI through Operator's conpty host. tmux and iTerm2-specific behavior applies only to other platforms.
	</Accordion>

	<Accordion title="Where does Operator store data?">
		Under `~/.operator` by default. Durable daemon state is SQLite under `~/.operator/data`; the same Operator home also contains the run file, managed worktrees and metadata, desktop webview data, and mobile configuration. Advanced daemon paths can be overridden with `OPERATOR_DATA_DIR` and `OPERATOR_RUN_FILE`.
	</Accordion>

	<Accordion title="Can I expose Operator on a remote server?">
		Do not expose the primary daemon listener. It is unauthenticated and fixed to `127.0.0.1`. Connect Mobile is the only built-in LAN path: it is opt-in, password-protected, plaintext, and intended only for a trusted home network.
	</Accordion>

	<Accordion title="What does Operator cost?">
		Operator is Apache-2.0 licensed. Agent usage is billed according to the provider account or subscription used by each installed harness. Chat records usage data when the provider reports it.
	</Accordion>

	<Accordion title="Does Operator upload my source code?">
		Operator coordinates local worktrees and invokes your installed agents and GitHub tooling. Those tools follow their own provider data policies. Operator's desktop renderer also sends anonymous usage events to PostHog in standard builds; session recording is disabled by default, and local paths and URLs are redacted if a time-boxed investigation enables it.
	</Accordion>

	<Accordion title="Can I still install Operator from npm?">
		The legacy `@operator-dev/opr` package remains available, but `0.10.0` is its final release and it will not receive updates. Prefer the [desktop download](/docs/installation). Existing npm users can run `opr start` to fetch and open the desktop build.
	</Accordion>

	<Accordion title="Can Chat and Terminal UI run at the same time for one session?">
		No. A session commits to one controller at a time. Compatible Claude Code and Codex sessions can hand off between interfaces, but Operator drains or interrupts the old controller before activating the new one.
	</Accordion>

	<Accordion title="How do I uninstall Operator?">
		Remove the desktop application using your operating system's normal process. If you also remove `~/.operator`, you permanently delete Operator's database, session history, managed state, desktop webview data, and mobile pairing configuration. Inspect and preserve any work you need first. Legacy CLI users can separately run `npm uninstall -g @operator-dev/opr`.
	</Accordion>
</Accordions>
