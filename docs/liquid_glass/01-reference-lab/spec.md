# Mobile glass reference lab — design

Date: 2026-09-26
Branch: `feat/mobile-glass-lab`, worktree `../Operator-glass-lab`
Project 1 of 4 in the "complete native Liquid Glass" roadmap.

## Why

The user wants the mobile glass to be complete and indistinguishable from native iOS 27 Liquid Glass: every component, animation and behaviour, first as a package, then applied across Operator. Apple publishes almost no numbers for Liquid Glass: no blur radii, durations, springs or sizes ([research/apple-inventory.md](../research/apple-inventory.md) §9). The only reliable way to match it is to measure native output.

The tab bar proved this method (commit 947f03e8e), but it was done by hand, one component at a time, on iOS 26.5. The target is now **iOS 27**, which changed the material:
- a darker edge;
- brighter specular highlights;
- more diffusion;
- a new automatic scroll edge.

This was checked side by side on 2026-09-26.

This project builds the instrument that every later project is measured with:
- a native iOS 27 catalog of every iPhone Liquid Glass component;
- a touch driver that plays identical gestures on the native catalog, on Operator's Flutter glass lab, and on Apple's own apps;
- a measuring harness that compares the recordings numerically and writes a report.

The roadmap:
1. **Reference lab (this spec).**
2. **Glass engine.** The material itself, retuned to iOS 27.
3. **Component package.** The glass is extracted into its own workspace package and every component is built.
4. **Operator rollout.** Applied per component batch.

Projects 2–4 each get their own spec. This project fixes no glass. It ends with a baseline report that becomes their backlog.

## Research inputs

These are committed beside this spec under `docs/liquid_glass/research/`:
- `apple-inventory.md` — the 80-item Apple component and behaviour inventory, iOS 27 deltas, numbers ledger, and "behaviours most implementations miss". It is the checklist of what "complete" means.
- `flutter-repos.md`, `non-flutter.md` — techniques for projects 2–3. They are not used here.
- `operator-audit.md` — every Operator screen and the component each one uses. It is used by project 4.

## Decisions (settled with the user)

- **Target look:** iOS 27, on the iPhone 17 Pro simulator "iPhone 17 Pro (iOS 27)", UDID `708879DD-8B2A-4547-863F-F49EE1474D8B`. The harness finds it by name and runtime, never by a hard-coded UDID.
- **Platform:** iPhone only. iPad, Mac, app icons, widgets and system-owned UI (keyboard, share sheet) are out of scope.
- **Touch approach A:** gestures are played by an XCUITest runner, identical across apps. Agent-driven taps and in-app injected touches are not used.

## Prototype findings (2026-09-26)

A throwaway prototype of the whole lab ran on the iOS 27 simulator before the plan was written. Every item below was measured, and the sections after this one already reflect it.

- **Toolchain.** A generated `.xcodeproj` (Xcode 16+ synchronized folders, no per-file entries) builds the app and UI test runner with Xcode 27. `TEST_RUNNER_`-prefixed variables reach the runner. `XCUIApplication(bundleIdentifier:)` drives GlassLab, Operator's debug build and Apple's Reminders, and `launchEnvironment` reaches the native app. All 60 native scene views compile against the iOS 27 SDK.
- **Flutter cannot read launch variables on iOS.** Dart's `Platform.environment` is empty there: it logged 0 entries. The Flutter lab therefore takes its scene from a launch file, `Documents/glass_lab/launch.json`, which the harness writes before each launch and the app deletes as it starts. Flutter semantics identifiers do reach XCUITest.
- **Still images are exact.** The driver takes lossless 1206 × 2622 screenshots with `XCUIScreen`. Two native recordings of the same scene gave a MAD of 0.00. Static comparisons use these screenshots, never video frames.
- **Recordings are variable-rate at up to 120 Hz.** The simulated iPhone 17 Pro display runs at 120 Hz and the recorder writes frames only when the screen changes, at irregular intervals. Resampling to a fixed 60 fps duplicated frames and faked one-frame timing differences. Motion is therefore analysed at the recorder's real timestamps and interpolated onto a 120 Hz grid.
- **Test-runner clock times do not map reliably onto video time.** The analysis window is found from content instead: the first frame that leaves the "ready" screenshot, to the last frame that matches the "settled" screenshot. Matching compares 24 pt tiles.
- **Dynamic Island.** The top 72 pt differ between screenshots and video, so they are excluded from matching and from the moving-area pass.
- **Touch input has a noise floor.** XCUITest touch timing varies slightly between runs. Motion is therefore split into separate events (each burst of change), and each native/Flutter event pair is aligned by best curve fit before comparing. Three native takes of `menu.bar` agreed as follows on the menu-open event:

  | Measure | Agreement |
  |---|---|
  | Width peak time | 8 ms |
  | Settle time | 17 ms |
  | Overshoot | 0.4 points |
  | Fitted spring response | 2.4% |

  The menu-close event was noisier, with the fitted response varying by up to 16%. So motion pass limits are max(fixed threshold, 1.5 × the native-vs-native noise recorded in `noise.json`).
- **iOS 27 tab bar.** The search tab sits inside the tab bar capsule as a fourth item, not as a separate circle. The native bar measured x 20, y 791, 362 × 62 pt.

## Native catalog app (GlassLab)

- SwiftUI, deployment target iOS 27.0, built with Xcode 27 against the iOS 27 simulator SDK, bundle id `dev.operator.glasslab`. UIKit is used only where a behaviour has no SwiftUI API.
- **Scene selection.** At launch the app reads the `GLASS_LAB_SCENE` environment variable (a scene id) and shows exactly that scene full screen. With no id it shows a scrollable index of all scenes, so a person can browse the catalog.
- **Bare mode.** When `GLASS_LAB_BARE=1`, the scene renders only its backdrop, with no chrome and no controls. The harness uses this frame to find glass geometry by difference.
- **Ready marker.** A scene exposes an element with accessibility identifier `scene.ready` once it has laid out, plus identifiers for any control a step targets by name.
- **Palette.** The Operator palette constants already in `GlassReference.swift` (dark and light), so tints and accents match what Operator uses.
- **Backdrops.** Every scene draws one of the backdrop PNGs edge to edge under the status bar. It reads them from the app's own `Documents/glass_lab/`, where `lab.py prepare` copies them. Both apps therefore show byte-identical content behind the glass. The scene named by the `GLASS_LAB_BACKDROP` launch variable is the one drawn.
- **Scrolling scenes.** These put `scroll.png` in a ScrollView under the chrome.

## Scene manifest (`scenes.json`)

A JSON array. Each entry:

```json
{
  "id": "menu.bar",
  "group": "presentations",
  "title": "Menu from a toolbar button",
  "inventory": "4.6",
  "app": "lab",
  "backdrops": ["stripes", "photo"],
  "appearances": ["light", "dark"],
  "steps": [
    {"wait": 0.8},
    {"tap": [363, 84]},
    {"wait": 1.2},
    {"tap": [200, 780]},
    {"wait": 1.0}
  ],
  "regions": {"chrome": [230, 60, 172, 330]},
  "track": "chrome"
}
```

- `app` is `lab` for catalog scenes; the harness runs it on both GlassLab and Operator. A bundle id means an Apple app reference, native only.
- `steps` vocabulary, all coordinates in points and all times in seconds:
  - `wait`, `tap [x,y]`, `doubleTap [x,y]`;
  - `press {at, duration}`;
  - `pressDrag {from, to, pressDuration, velocity, hold}`, which maps to XCUITest `press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)`, with velocity in pt/s or `"default"`;
  - `tapElement "<accessibility id>"`.
- XCUITest cannot draw arbitrary multi-point paths through public API. Scenes are therefore designed around single press-drag-release gestures, and the vocabulary stays within public API.
- `regions` are named rectangles in points. `track` names the region whose geometry and brightness are followed over time. The first region is the default.

## Driver (GlassLabDriver)

- One XCUITest method, `testScene`, reads the scene id and target bundle id from its environment. The harness passes them through `xcodebuild` as `TEST_RUNNER_GLASS_SCENE` and `TEST_RUNNER_GLASS_TARGET`, since Xcode forwards `TEST_RUNNER_`-prefixed variables to the runner.
- It launches the target with `XCUIApplication(bundleIdentifier:)`, with `launchEnvironment` carrying `GLASS_LAB_SCENE` and, when asked, `GLASS_LAB_BARE`.
- It waits up to 20 s for `scene.ready`, then plays the steps. It uses `app.coordinate(withNormalizedOffset: .zero).withOffset(...)` so points mean the same thing on every target.
- **Steps.** The harness passes the scene's steps as JSON in `TEST_RUNNER_GLASS_STEPS`, so the runner never needs the manifest.
- **Screenshots and timing.** After `scene.ready` and a 1.5 s settle, the driver writes a lossless `ready.png` to the folder named by `TEST_RUNNER_GLASS_OUT`. It then plays the steps, settles again, and writes `settled.png` and `timing.json`.
- **Missing scenes.** When the target shows `scene.missing`, the driver skips the steps and records `missing: true`.
- Apple app references are launched the same way, without scene environment variables, and wait on the app's own first element instead of `scene.ready`.

## Operator's Flutter lab

This is the existing debug-only `/glass-lab` route in `lib/core/widgets/glass/lab/`, reached from `main.dart` when a lab scene is requested.
- **Runtime selection.** In debug builds, `main()` reads and deletes `Documents/glass_lab/launch.json`, which holds `{scene, backdrop, bare}`. The harness writes that file before every launch, so one build serves every scene; `Platform.environment` is empty on iOS. `path_provider`, already in the lock file through `drift_flutter`, becomes a direct dependency to find the folder. The compile-time `--dart-define=GLASS_LAB_SCENE` path is removed, together with the in-app injected touch (`_injectLiftTouch`), which the driver replaces.
- **Scene registry.** Every manifest scene id with `app: lab` resolves to a widget. Scenes built from components Operator already has use them:
  - `tabbar.*` uses `GlassTabBar`;
  - `button.*` uses `GlassButton`;
  - `sheet.detents` and `sheet.scroll` use `AppSheet`;
  - `material.edge.*` uses `ScrollEdgeEffect`;
  - `navbar.inline` uses `GlobalAppbar`;
  - `material.regular`, `material.tinted` and `material.clear` use `GlassSurface`;
  - `material.interactive` uses a pressable `GlassSurface`.

  Every other id renders a placeholder: backdrop plus a centred "missing: <id>" label, with a `scene.missing` semantics identifier. The report can then show coverage.
- **Backdrops.** The Flutter lab loads the same PNGs from the app's data container. `lab.py prepare` copies them to `<container>/Documents/glass_lab/` (found with `simctl get_app_container ... data`), and the lab reads them from the same folder. They are not added to the app's asset bundle, so release builds do not ship them.
- **Markers and layout.** Semantics identifiers `scene.ready` and the per-control ids named in steps. Layouts copy the native scene's geometry, which `lab.py geometry <id>` reports from the native recording.
- Layout mismatches the report finds against the native geometry are backlog items for projects 2–4, not work for this project. The exception is the existing tab bar, button, sheet and scroll edge scenes, which must be positioned to match (see Done).

## Harness (`harness/lab.py`)

Python 3 with PIL and numpy only (both installed), plus `ffmpeg` and Xcode's `xcrun`/`xcodebuild`. No other installs. Commands:

- **`lab.py build`** builds three things for the iOS 27 simulator:
  - GlassLab and GlassLabDriver (`xcodebuild build-for-testing`);
  - Operator in debug with `flutter build ios --simulator --debug --config-only`, then `xcodebuild` on `ios/Runner.xcworkspace` with `-derivedDataPath build/dd`. `flutter build ios` alone fails under Xcode 27.

  It then installs both apps on the simulator.
- **`lab.py prepare`** handles simulator setup:
  - finds or boots "iPhone 17 Pro (iOS 27)";
  - sets the status bar override (9:41, full battery, full bars);
  - copies the backdrops into Operator's container;
  - runs the Apple app first-run preparation.
- **`lab.py run <scene-id|group|all> [--app native|flutter|both] [--appearance light|dark|both] [--backdrop <id>] [--a11y none|reduce-transparency|increase-contrast|reduce-motion]`** runs, for each combination:
  1. Sets the appearance (`simctl ui appearance`) and the accessibility setting.
  2. Runs the driver once in bare mode (no steps) for the lossless `bare/ready.png`.
  3. Starts `simctl io recordVideo --codec=h264` and waits for its "Recording started" line. It runs `xcodebuild test-without-building -only-testing:GlassLabDriver/DriverTests/testScene` with the scene's steps, then stops the recording with SIGINT and waits for the file to finalise. Output goes to `build/glass_lab/runs/<timestamp>/<scene>/<appearance>-<backdrop>[-<a11y>]/<app>/`.
  4. Leaves frame extraction to `report`, which works at the recording's real frame timestamps.
- **`lab.py report [<run dir>]`** computes metrics and writes `report.html` in the run directory. With no argument it uses the latest run.
- **`lab.py baseline`** runs `prepare`, then every scene in both apps in both appearances with every listed backdrop, plus the accessibility variants, then `report`.
- **`lab.py geometry <scene-id>`** prints the native glass bounding boxes of a scene, in points, found by differencing against the bare frame. Flutter scene authors use it.
- **`lab.py repeat [<scene-id>] [--times 3]`** records a scene natively several times and compares every pair. It checks that still images agree (MAD ≤ 1.0) and writes the largest native-vs-native motion difference per measure to `noise.json`. With no scene id it covers `material.regular`, `tabbar.rest`, `tabbar.drag` and `menu.bar`.

### Metrics (`metrics.py`, `align.py`, `springfit.py`)

Static math uses the full 3× lossless screenshots. Motion math uses video frames scaled to points (1×), which keeps memory small. Results are reported in points and milliseconds.

- **Window and events.** The window runs from the first recorded frame that leaves the `ready` screenshot to the last frame that matches the `settled` screenshot. Matching uses 24 pt tiles and skips the top 72 pt. Inside the window, frames of the tracked region are extracted at their real timestamps. An event starts at a frame differing from its predecessor by a MAD above 0.5 (0–255 scale). It ends after 150 ms without such a change, and events with no real travel are dropped. Each event is resampled onto a 120 Hz grid. Native and Flutter events are paired by order and aligned by the lag (±150 ms) that best fits all their moving series together, each normalised by its native travel. Alignment only lines the curves up for the RMS difference and the overlay charts. Springs, peak, settle and overshoot are measured on each app's full event. Rest scenes have no events.
- **Region.** The tracked region is the union of three areas, padded by 12 pt: the glass boxes in the ready and settled screenshots, plus every 8 pt tile that changes during the window.
- **Static (the `ready` and `settled` screenshots, per region):**
  - MAD against native, per RGB channel and averaged;
  - mean luminance (Rec. 709) difference;
  - rim profile: luminance sampled along the vertical line through the region's glass centre, 12 pt either side of the top and bottom edges, compared point by point;
  - glass bounding box: pixels differing from the bare frame by more than 6, in connected components. Native's box is its largest component. Flutter's box is the union of its components that overlap native's box, so it measures the same element even when Operator's glass is faint and only its contents stand out, or when the largest Flutter shape is a different element. When nothing overlaps, the box is unmatched and fails. Reported as x, y, width, height and the edge and centre differences to native in points.
- **Motion (per event, on the 120 Hz grid):**
  - glass bounding box width, height and centre, plus mean luminance, as time series;
  - differences to native: RMS error, peak time (ms), peak overshoot (percent of travel) and settle time (ms, within 2% of final). These are measured only when a series travels at least 4 pt, or 3 luminance levels;
  - the event counts of native and Flutter must match;
  - `springfit.py` fits a damped oscillator to each normalised series by a numpy grid search over response 0.05–1.5 s and damping fraction 0.1–1.2. It reports the fitted response and damping for native and Flutter, so later projects can copy springs directly.
- **Initial pass thresholds**, used later to judge projects 2–4:

  | Measure | Threshold |
  |---|---|
  | Region MAD | ≤ 4.0 |
  | Luminance difference | ≤ 3.0 |
  | Rim profile RMS | ≤ 6.0 |
  | Bounding box difference | ≤ 1 pt on each edge |
  | Peak and settle time | ≤ 17 ms (two 120 Hz frames) |
  | Overshoot | ≤ 2 points of percent |
  | Fitted response | within 5% |
  | Fitted damping | within 0.05 |

  A scene passes when every measure passes. Thresholds live in one table in `metrics.py`. Motion limits are raised to 1.5 × the scene's recorded native-vs-native noise wherever that is larger. Spring fits count only when the fit's RMS error is under 0.15.

### Report (`report.py`)

`report.html` is self-contained apart from image files in the run directory. It has:

- **Summary:** counts of cases passing, failing, missing in Flutter, native-only references, and harness errors.
- **Coverage table:** one row per scene. Columns are the Flutter status (implemented or missing), worst measure, pass or fail, and a link.
- **Per-scene page**, for each appearance and backdrop:
  - settled frames side by side: native, Flutter, and a difference map ×4;
  - a filmstrip of both recordings aligned at onset, one frame every 50 ms for 1 s after onset;
  - the time-series curves as inline SVG, native against Flutter;
  - the rim profiles as inline SVG;
  - the metric table with pass or fail per measure.
- **Apple app references:** filmstrips and fitted springs only.

## Testing the tooling

- `harness/tests/` uses `unittest` (no pytest), with synthetic frames made by numpy:
  - onset alignment recovers a known offset to within 1 frame;
  - the spring fit recovers a known response and damping to within 5% and 0.05;
  - the bounding-box finder recovers a drawn rounded rectangle to within 1 px;
  - the rim profile sampler returns the drawn gradient;
  - the metric thresholds classify known inputs correctly.

  Run with `python3 -m unittest discover tool/glass_lab/harness/tests`.
- **Repeatability check (`lab.py repeat`).** The same native scene recorded three times must agree. Still images must be exact: MAD ≤ 1.0; the prototype measured 0.00. The motion noise floor is written to `noise.json`, and any motion measure's pass limit is max(fixed threshold, 1.5 × its recorded noise). The originally specified one-frame bar below is the target, reported rather than enforced:
  - settled MAD under 1.0 and bounding box identical, for `material.regular` and `tabbar.rest`;
  - peak and settle times within one frame, for `tabbar.drag` and `menu.bar`.

  If this fails, the rig is not trustworthy and fixing it comes before anything else.
- Flutter changes pass `flutter analyze` ("No issues found!") and `flutter test`. Tests pin:
  - scene id parsing from the environment;
  - registry resolution of every `app: lab` manifest id, read from the real `scenes.json`;

## Risks (resolved by the prototype)

The prototype settled each open question:

- **XCUITest reach.** XCUITest launches and drives GlassLab, Operator's debug Flutter build and an Apple app by bundle id on the iOS 27 simulator, and it sees Flutter semantics identifiers and labels. `launchEnvironment` reaches the native app but not Dart, so Flutter uses the launch file.
- **Runner variables.** `TEST_RUNNER_`-prefixed variables reach the runner.
- **Touch timing.** Timing is repeatable enough for the primary event of a gesture (menu open: 8 ms peak, 2.4% response), but not every event of every gesture. `noise.json` absorbs the rest.
- **Accessibility settings.** All three can be scripted, and each app sees them on its next launch:
  - Reduce Motion: `defaults write com.apple.Accessibility ReduceMotionEnabled`;
  - Reduce Transparency: `EnhancedBackgroundContrastEnabled`;
  - Increase Contrast: `simctl ui increase_contrast`.
- **Recording.** `simctl io recordVideo` writes variable-rate frames with accurate timestamps at up to 120 Hz. The analysis uses the real timestamps rather than resampling to a fixed rate.
- **Flutter debug builds.** Simulator builds are debug (JIT). Timing is wall-clock and valid, but a dropped frame shows as a stall. The report lists frame gaps longer than 25 ms inside Flutter motion, so a stall is not mistaken for a spring difference.
- **Duration.** One scene and one app take about 36 s. The full baseline is 186 appearance-and-background combinations times two apps, plus the accessibility runs, so it takes around four hours. Run it in the background.
