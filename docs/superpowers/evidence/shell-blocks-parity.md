## Known limits

- Durable shell blocks are Unix/tmux-only. Windows keeps a working raw ConPTY terminal and reports durable blocks unavailable until a ConPTY-native single-owner capture path exists.
- Durable history retains the newest 100 blocks per terminal. Each block retains the newest 5,000 output lines and at most 8 MiB of raw bytes, with omitted line and byte counts stored.
- The helper journal is bounded to eight sealed 1 MiB segments plus one active segment. If an offline daemon falls behind that bound, the oldest bytes are intentionally lost, a gap is recorded, the torn partial block is abandoned, and assembly resumes at the next valid prompt.
- The Tier-2 OSC 7000 `id` is an in-flight reconnect upsert aid only, consumed by the frontend's `feedToCore` path, not by the terminal core: `packages/terminal/crates/vt-core/src/block_grid.rs`'s `set_meta_field` recognizes only `cmd`/`cwd`/`branch`/`exit`/`start_ms`/`end_ms`, and a rendered block's id comes from the core's own internal per-OSC133-`A` counter, not from that opaque id. `feedToCore` strips only the OSC 7000 marker bytes, not the enclosing OSC 133 boundary. If a live reattach ever re-delivers OSC 133-bounded bytes for a block already loaded from history, the real core would render a duplicate block. This is cosmetic only: the persisted `terminal_blocks` row for that block stays singular. It is unproven whether a tmux client repaint actually re-emits those bytes for already-painted content; the real-core integration test that would settle it does not exist yet (`BlockTerminal.test.tsx`'s dedup coverage runs only against a `MockCore` that keys blocks by that id in a `Map`, so it cannot prove or disprove real-core behavior).
